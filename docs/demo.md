# The demo environment (`devenv/`)

## Containers (compose project `zuul-git-stream-demo`)

| Service | Image | Role |
|---------|-------|------|
| `zk`, `mysql` | mirrors of zookeeper / mariadb | Zuul's dependencies |
| `init` | `localhost/zuul:dev` | one shot: ZooKeeper TLS certs (`init.sh`) |
| `git-stream` | `localhost/zuul-git-stream:latest` (`Containerfile`) | the forge, config `git-stream.toml`, port 8090, volume `forge`; holds no job definitions |
| `gitserver` | git-stream image | `gitserver.py`: `repos/zuul-config` as a read-only git repository over HTTP on 8091 (stands in for the real config repos), volume `gitrepos` |
| `seed` | git-stream image | one shot: `seed.py` announces the starting state (see below) |
| `scheduler`, `merger`, `web`, `executor` | `localhost/zuul:dev`, `localhost/zuul-executor:dev` | **unmodified** Zuul, built from source |
| `logs` | `localhost/zuul:dev` | serves job logs on 8000 (`logserver.py`) |
| `demo-ui` | git-stream image | demo page on 8080 (`demo-ui/app.py`, `index.html`) |

Zuul images are built from Zuul's own Dockerfile at the commit pinned in
`common.sh` (`ZUUL_REF`) because upstream images are amd64 only and the
executor's bubblewrap can't run under emulation.  Set `ZUUL_IMAGE` /
`ZUUL_EXECUTOR_IMAGE` to use other images.

Ports: 8080 demo UI, 8090 git-stream, 9000 Zuul web, 8000 logs, all
published on 127.0.0.1 only: git-stream runs with `insecure = true` (an open
stream), so the demo must not be reachable from the network.  `DEMO_BIND`
changes that (`DEMO_BIND=0.0.0.0 ./deploy.sh` for one run, or in `.env`); `DEMO_HOST` then controls the address printed for
other computers.

Secrets: `deploy.sh` creates `.env` from `.env.example` with random values
and renders `etc_zuul/zuul.conf` from `etc_zuul/zuul.conf.in` (neither is
committed).  `clean.sh` removes both with the volumes.  After pulling a
version that moved the secrets out of the repo, run
`./clean.sh -y --keep-images` once: the old database and keystore keep the
old passwords.

## Scripts

- `deploy.sh [--open]`: start podman machine if needed, build Zuul
  images once, build the git-stream image, `compose up`, recreate
  git-stream/demo-ui/gitserver/seed, wait until Zuul is running and has the tenant's
  pipelines (`wait_ready` in `common.sh`).
- `stop.sh [--keep-machine]`: stop containers (and the podman machine),
  keep everything.
- `clean.sh [-y] [--keep-images]`: remove containers, volumes, network,
  images, Zuul source.  Note: it also removes `localhost/zuul:dev`, which
  the sibling kafka demo shares.
- `demo.sh`: `deploy.sh` then an interactive walkthrough (needs a TTY).
- `check.sh`: last builds from Zuul's API.

## Zuul configuration

- `etc_zuul/zuul.conf.in` (rendered to `zuul.conf` by `deploy.sh`):
  `[connection gitlab]` → git-stream, tokens from `.env`, matching
  git-stream's environment (`compose.yaml`); `[connection config-git]`, Zuul's
  plain `git` driver, → `gitserver` (polled every 10 s).  Jobs run on the
  executor (no nodes), allowed because they're in the trusted `zuul-config`
  project.
- `etc_zuul/main.yaml`: tenant `example-tenant`; config project
  `zuul-config` on `config-git` (a real git repository, as in production);
  untrusted `bundles` and `ci-tool` on the gitlab connection.  Those two are
  placeholders in git-stream (an empty tree each): git-stream never holds job
  definitions, it only sends messages.
- `etc_zuul/site-variables.yaml`: generated by `deploy.sh`
  (`demo_host`, used for log links).

`repos/zuul-config` is committed into a bare repository by `gitserver.py`
every time that container starts.  **After changing it, run `./deploy.sh`**
(it restarts `gitserver`); Zuul sees the new commit within `poll_delay`
(10 s) and reloads the tenant.

`seed.py` (the `seed` service) sends the starting state as messages, and is
safe to run again: `create_project` for `bundles` and `ci-tool`, and a `push`
of ci-tool's first data, `{"broken_jobs": ["bundle-security"]}`.  The
scheduler waits until `GET .../projects/ci-tool/data` answers, so the tenant
loads after it.

### Pipelines (`repos/zuul-config/zuul.d/pipelines.yaml`)

- `bundle-test` (independent): MR `opened`/`changed`, or comment
  `recheck`.  Reports start/results as comments; approves on success,
  unapproves on failure.
- `bundle-rerun` (independent): comment starting with `rerun`.

### Jobs

- `bundle-dispatch` → `playbooks/bundle/dispatch.{yaml,py}`: reads the
  MR's data (`GET .../merge_requests/<iid>/data?sha=<patchset>`: id, flaky)
  and, in `bundle-rerun`, the newest
  `rerun ...` note from git-stream's API.  Grammar:
  - `rerun failed`: jobs whose latest result on this MR isn't SUCCESS
    (from Zuul's builds API, filtered by `change`)
  - `rerun all`
  - `rerun <job> ...`: `bundle-` prefix optional
  - optional `flaky=N` token (0-1) anywhere.
  Returns `zuul.child_jobs`, `bundle_id`, `flaky` via `zuul_return`.
- `bundle-*` (10 jobs, parent `bundle-test-base`, `playbooks/bundle/test.yaml`):
  print steps, then fail if the job is in ci-tool's `broken_jobs` (the
  "bug"), else fail at random with probability `flaky`.  ci-tool's state is
  its data in git-stream: the Depends-On ci-tool MR's data (found in
  `zuul.items`) if there is one, else what ci-tool last announced
  (`GET .../projects/ci-tool/data`).
- `base`: no nodes, `post-logs.yaml` copies logs to the log server.

## Demo UI (`demo-ui/app.py`)

Stdlib HTTP server.  It sends events to git-stream (`POST /api/stream`)
and proxies git-stream's and Zuul's APIs.

| Endpoint | Does |
|----------|------|
| `POST /api/bundle {"action": "new", "flaky"}` | `open_mr` on bundles with key `b-NNNN` and the bundle as `data` |
| `POST /api/bundle {"action": "failed"\|"all"\|"selected", "bundle_id", "jobs", "flaky"}` | comment `rerun ...` (refused while the bundle is running) |
| `POST /api/bundle {"action": "with-fix", "bundle_id", "flaky"}` | `update_mr`: adds `Depends-On: <ci-tool fix URL>` and sets `flaky` in the bundle's `data` |
| `POST /api/ci-tool {"action": "fix-open"\|"fix-merge"\|"break"}` | ci-tool fix MR (key `fix-parse-manifest`, data `{"broken_jobs": []}`), merge it (its data becomes ci-tool's current data), or push the bug back as data |
| `GET /api/bundles` | MRs + per-job latest verdict + busy/approved/escalated |
| `GET /api/ci-tool` | `broken_jobs` (ci-tool's current data) + fix MR |
| `GET /api/status`, `/api/builds`, `/api/sent`, `/api/deliveries`, `/api/escalations` | Zuul status, builds, events sent, webhook deliveries, escalations |
| `GET /api/metrics` | per-job run/pass/fail counts from git-stream's SQLite metrics store |
| `GET /metrics` | the metrics page: charts and filters over builds, escalations, webhooks and messages (`metrics.html`, `metrics.js`) |
| `GET /api/metrics/{runs,escalations,deliveries,messages}?...` | git-stream's counting endpoints (`/api/stream/metrics/<kind>`), proxied; errors pass through; `STREAM_TOKEN` (env) is added for messages |

The page rewrites `http://git-stream:8090` links to the browser's host.

### The metrics page (`/metrics`)

Charts and filters over what git-stream recorded, in four sections: jobs
(results, failure rate, runs over time, durations, pipelines), bundles (runs
per bundle, escalations over time, escalated jobs), webhooks (deliveries over
time, delivered or not, by kind) and messages (over time, by action, sender
and outcome), with totals on top.  Filters: time range (quick or custom, UTC),
project, job, result, pipeline, bundle, and the webhook and message fields;
they are in the address, so a view can be shared, and the page refreshes every
10 seconds.  It loads Chart.js from `cdnjs.cloudflare.com` (pinned to one
version), so it needs internet access; without it the numbers show as tables.
The metrics sections need `[metrics] path` (the demo has it); the message
charts need a stream token if the stream is not open (set `STREAM_TOKEN` on
the `demo-ui` container).  Builds recorded before the metrics fix have no
times, so they count in totals but not in time charts.

## Scenario and expected results

1. New bundle (flaky 0.3): ~3 random failures + `bundle-security`
   (ci-tool bug).
2. git-stream retries automatically: flaky jobs pass; security fails 3
   times → escalated (`/escalations`, MR page, demo panel).  ~2 minutes.
3. Open the ci-tool fix, "Test with fix" (flaky 0): new MR version (count
   resets), 10/10, Zuul approves.
4. Merge the fix (its data becomes ci-tool's current data), or break it
   again (a push of data).

## Verifying without a browser

```sh
B=$(curl -s -X POST localhost:8080/api/bundle -d '{"action":"new","flaky":0.3}' \
    | python3 -c 'import json,sys; print(json.load(sys.stdin)["key"])')
# wait ~2 min, then:
curl -s localhost:8090/api/stream/escalations
curl -s "localhost:8090/api/v4/projects/bundles/merge_requests/1/notes?sort=asc"
podman logs zuul-git-stream-demo_git-stream_1 | grep -E 'rerun|Escalating'
```

Job logs: `http://localhost:8000/<build uuid>/job-output.txt`
(`log_url` in Zuul's builds API).

## Where state lives

The `forge` podman volume (`/srv/git-stream`) holds everything git-stream
persists across restarts:

- `state.db` — the forge's own state (projects, merge requests, notes,
  approvals, the dedup list, per-MR retry state).  In-memory while running;
  this is the durability mirror, written on every change.
- `metrics.db` — the activity log (one row per completed build, escalation,
  and webhook delivery).  See the `/metrics` page or `GET
  /api/stream/metrics`.
- `repos/` — the placeholder git repositories Zuul clones (one empty-tree
  commit per project, one commit per MR version).  The message log and the MR
  and project `data` tables are in `state.db`.

Inspect it without stopping the demo:

```sh
podman exec zuul-git-stream-demo_git-stream_1 sh -c 'ls -la /srv/git-stream/*.db'
```

The `gitrepos` volume holds the bare repository `gitserver` serves
(`zuul-config`).  `clean.sh` deletes both volumes, which is how you reset the
demo to a pristine forge.
