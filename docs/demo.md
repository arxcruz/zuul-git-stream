# The demo environment (`devenv/`)

## Containers (compose project `zuul-git-stream-demo`)

| Service | Image | Role |
|---------|-------|------|
| `zk`, `mysql` | mirrors of zookeeper / mariadb | Zuul's dependencies |
| `init` | `localhost/zuul:dev` | one shot: ZooKeeper TLS certs (`init.sh`) |
| `git-stream` | `localhost/zuul-git-stream:latest` (`Containerfile`) | the forge, config `git-stream.toml`, port 8090, volume `forge` |
| `scheduler`, `merger`, `web`, `executor` | `localhost/zuul:dev`, `localhost/zuul-executor:dev` | **unmodified** Zuul, built from source |
| `logs` | `localhost/zuul:dev` | serves job logs on 8000 (`logserver.py`) |
| `demo-ui` | git-stream image | demo page on 8080 (`demo-ui/app.py`, `index.html`) |

Zuul images are built from Zuul's own Dockerfile at the commit pinned in
`common.sh` (`ZUUL_REF`) because upstream images are amd64 only and the
executor's bubblewrap can't run under emulation.  Set `ZUUL_IMAGE` /
`ZUUL_EXECUTOR_IMAGE` to use other images.

Ports: 8080 demo UI, 8090 git-stream, 9000 Zuul web, 8000 logs.
`DEMO_HOST` controls the address printed for other computers.

## Scripts

- `deploy.sh [--open]`: start podman machine if needed, build Zuul
  images once, build the git-stream image, `compose up`, recreate
  git-stream/demo-ui, wait until Zuul is running and has the tenant's
  pipelines (`wait_ready` in `common.sh`).
- `stop.sh [--keep-machine]`: stop containers (and the podman machine),
  keep everything.
- `clean.sh [-y] [--keep-images]`: remove containers, volumes, network,
  images, Zuul source.  Note: it also removes `localhost/zuul:dev`, which
  the sibling kafka demo shares.
- `demo.sh`: `deploy.sh` then an interactive walkthrough (needs a TTY).
- `check.sh`: last builds from Zuul's API.

## Zuul configuration

- `etc_zuul/zuul.conf`: `[connection gitlab]` → git-stream, tokens
  matching `git-stream.toml`.  Jobs run on the executor (no nodes),
  allowed because they're in the trusted `zuul-config` project.
- `etc_zuul/main.yaml`: tenant `example-tenant`; config project
  `zuul-config`, untrusted `bundles`, `ci-tool`, all on the gitlab
  connection.
- `etc_zuul/site-variables.yaml`: generated by `deploy.sh`
  (`demo_host`, used for log links).

`repos/` are seed projects, created in git-stream on its first start
(`[server] seed`).  **Changing `repos/` after the first start has no
effect** until the `forge` volume is wiped (`clean.sh --keep-images`).

### Pipelines (`repos/zuul-config/zuul.d/pipelines.yaml`)

- `bundle-test` (independent): MR `opened`/`changed`, or comment
  `recheck`.  Reports start/results as comments; approves on success,
  unapproves on failure.
- `bundle-rerun` (independent): comment starting with `rerun`.

### Jobs

- `bundle-dispatch` → `playbooks/bundle/dispatch.{yaml,py}`: reads the
  MR's `bundle.yaml` (id, flaky) and, in `bundle-rerun`, the newest
  `rerun ...` note from git-stream's API.  Grammar:
  - `rerun failed`: jobs whose latest result on this MR isn't SUCCESS
    (from Zuul's builds API, filtered by `change`)
  - `rerun all`
  - `rerun <job> ...`: `bundle-` prefix optional
  - optional `flaky=N` token (0-1) anywhere.
  Returns `zuul.child_jobs`, `bundle_id`, `flaky` via `zuul_return`.
- `bundle-*` (10 jobs, parent `bundle-test-base`, `playbooks/bundle/test.yaml`):
  print steps, then fail if the job is in ci-tool's `tool.yaml`
  `broken_jobs` (the "bug"), else fail at random with probability
  `flaky`.  `required-projects: ci-tool` so a Depends-On ci-tool MR is
  checked out speculatively merged.
- `base`: no nodes, `post-logs.yaml` copies logs to the log server.

## Demo UI (`demo-ui/app.py`)

Stdlib HTTP server.  It sends events to git-stream (`POST /api/stream`)
and proxies git-stream's and Zuul's APIs.

| Endpoint | Does |
|----------|------|
| `POST /api/bundle {"action": "new", "flaky"}` | `open_mr` on bundles with key `b-NNNN`, `bundle.yaml` |
| `POST /api/bundle {"action": "failed"\|"all"\|"selected", "bundle_id", "jobs", "flaky"}` | comment `rerun ...` (refused while the bundle is running) |
| `POST /api/bundle {"action": "with-fix", "bundle_id", "flaky"}` | `update_mr`: adds `Depends-On: <ci-tool fix URL>` and rewrites `flaky` in `bundle.yaml` |
| `POST /api/ci-tool {"action": "fix-open"\|"fix-merge"\|"break"}` | ci-tool fix MR (key `fix-parse-manifest`), merge it, or push the bug back |
| `GET /api/bundles` | MRs + per-job latest verdict + busy/approved/escalated |
| `GET /api/ci-tool` | `broken_jobs` on master + fix MR |
| `GET /api/status`, `/api/builds`, `/api/sent`, `/api/deliveries`, `/api/escalations` | Zuul status, builds, events sent, webhook deliveries, escalations |
| `GET /api/metrics` | per-job run/pass/fail counts from git-stream's SQLite metrics store (`/metrics` page) |

The page rewrites `http://git-stream:8090` links to the browser's host.

## Scenario and expected results

1. New bundle (flaky 0.3): ~3 random failures + `bundle-security`
   (ci-tool bug).
2. git-stream retries automatically: flaky jobs pass; security fails 3
   times → escalated (`/escalations`, MR page, demo panel).  ~2 minutes.
3. Open the ci-tool fix, "Test with fix" (flaky 0): new MR version (count
   resets), 10/10, Zuul approves.
4. Merge the fix (push to ci-tool master), or break it again.

## Verifying without a browser

```sh
B=$(curl -s -X POST localhost:8080/api/bundle -d '{"action":"new","flaky":0.3}' \
    | python3 -c 'import json,sys; print(json.load(sys.stdin)["key"])')
# wait ~2 min, then:
curl -s localhost:8090/api/stream/escalations
curl -s "localhost:8090/api/v4/projects/bundles/merge_requests/1/notes?sort=asc"
podman logs zuul-git-stream-demo_git-stream_1 | grep -E 'rerun|Escalating'
```

Job logs: `http://localhost:8000/<build uuid>/job-output.txt`
(`log_url` in Zuul's builds API).
